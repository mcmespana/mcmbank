## Findings considered and rejected / deferred (not planned)

These were surfaced during the audit but are intentionally **not** turned
into standalone plans right now — either lower leverage, needing a
maintainer decision this document can't make, or better handled as part of
a plan above. Re-audit these on the next `improve` pass rather than
re-discovering them from scratch:

- **Rate limiting on admin/auth endpoints** (SECURITY-AUDIT.md §5.2): needs
  an infra choice (Vercel-native rate limiting vs. a library like
  `@upstash/ratelimit`) that's a maintainer call, not something to pick
  silently in an executor plan. Revisit once 001 has landed and closed the
  higher-severity unauthenticated-access gap it would otherwise mitigate.
- **`console.log`/`console.error` cleanup across 145+ call sites**
  (SECURITY-AUDIT.md §5.4): real but low-severity (browser-side logs, no
  server secrets exposed per the original audit's own assessment) and
  large/tedious. Worth a dedicated plan if prioritized, not bundled here.
- **Content-Security-Policy header**: deliberately excluded from plan 011
  — a CSP tuned wrong is worse than none, and getting it right for this
  app's actual script/style sources (Radix, Recharts, Supabase) needs
  page-by-page manual QA. Do this as its own focused plan with a testing
  checklist, not a bundled line item.
- **Hardcoded emails in `lib/actions/auth.ts`** (SECURITY-AUDIT.md §5.6):
  real but trivial and unrelated in theme to the plan 011 bundle; low
  enough priority to fold into whatever plan next touches that file, or
  its own 10-minute fix.
- **`@typescript-eslint/no-explicit-any` re-enablement**
  (SECURITY-AUDIT.md §6.1): would require fixing every existing `any` usage
  across the codebase to re-enable cleanly — large, diffuse effort with
  unclear leverage until someone scopes how many `any`s actually exist.
  Not planned; recommend a follow-up audit specifically counting/
  categorizing `any` usage before committing to this.
- **Next.js Image Optimizer (`unoptimized: true`)** (SECURITY-AUDIT.md
  §6.2): pure performance/cost item (no security angle beyond what's
  already covered by the header hardening in plan 011); low urgency for an
  internal delegation-management tool with presumably modest image volume
  (bank/category icons). Revisit if page-load performance becomes a
  reported problem.
- **RLS policy verification across all Supabase tables**
  (SECURITY-AUDIT.md §8, final bullet): the entire client-side security
  model in this app (`SECURITY-AUDIT.md` §4.1–4.2) depends on RLS being
  correctly configured, but auditing/writing RLS policies requires
  Supabase dashboard/CLI access this session didn't have — **this is the
  single most important unplanned item**. Strongly recommend the
  maintainer runs a dedicated RLS audit (ideally with the Supabase MCP
  tools or CLI, listing every table's policies against expected
  delegation-scoping) before treating any of the client-side delegation
  filtering in `hooks/use-movimientos.ts` etc. as a real security boundary.
- **`hooks/use-transacciones-original.ts` / `use-delegaciones-original.ts`**:
  plan 008 confirmed and deleted `use-cuentas-original.ts` as dead code;
  these two similarly-named files were flagged by the original Semgrep
  scan but not independently re-verified as dead in this pass — check with
  `grep -rl` before assuming; if dead, a trivial follow-up deletion.
- **Full audit-trail/logging for privileged operations**
  (SECURITY-AUDIT.md §8, "Implementar audit logging"): a real
  larger-scope feature (who changed what, when, for compliance/accounting
  trust in a financial app) — grounded direction finding, not a bug fix.
  Recommend as a future *design* plan (define the audit log schema, which
  operations to cover, retention) rather than jumping straight to
  implementation.
- **UX-06 (`onCreateNew` divergence between transaction-create-panel and
  transaction-detail)**: folded into plan 013 as an investigate-first step
  rather than a standalone plan, since it was LOW-confidence at audit time
  (smell, not confirmed divergence).
