## Why this matters

`package.json` pins 27 dependencies to the string `"latest"` instead of a
real semver version — including `@supabase/ssr` and `@supabase/supabase-js`,
which this entire app's auth/session/query layer is built on. A `"latest"`
pin means a routine `pnpm install` (fresh machine, CI cache miss, dependency
added later) can silently pull in a new major version with breaking
changes, producing a build or runtime failure with no corresponding code
change in the diff to explain it. `SECURITY-AUDIT.md` §2.3 already flagged
this as a reproducibility/security issue. Note that two other items from
that same audit section — the Next.js CVEs and the abandoned `xlsx` package
— are **already resolved** in the current `package.json` (confirmed at
plan-writing time: `next` is pinned to `^16.1.6`, `xlsx` now points at the
maintained SheetJS CDN tarball `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`)
— do not re-do that work, this plan is scoped to the remaining `"latest"`
pins only.

## Scope

**In scope**:
- `package.json` — replace every `"latest"` value with a `^`-prefixed
  version matching the currently-installed resolved version.
- `pnpm-lock.yaml` — regenerated by `pnpm install` after the `package.json`
  edit (should be a no-op diff if versions match what's already resolved).

**Out of scope**:
- Actually upgrading any package to a newer version — this plan pins to
  what's *currently installed*, it does not change behavior. A separate
  future plan should handle deliberate upgrades.
- Setting up Renovate/Dependabot or any automated-update tooling — note as
  a recommendation in your summary, don't configure it.
- `next` and `xlsx` — already fixed, not in scope (confirm this remains
  true when you start; if `package.json` has drifted back to `"latest"` for
  either, that's an unexpected regression — STOP and report rather than
  silently "fixing" it as part of this batch, since it suggests something
  reverted the prior fix).

## Steps

### Step 1: Get the resolved version for every `"latest"` dependency

```bash
grep -n '"latest"' package.json
pnpm ls --depth 0
```

Cross-reference: for each package name pinned to `"latest"`, find its
actually-installed version in the `pnpm ls` output.

### Step 2: Edit `package.json`

For each `"latest"` entry, replace with `"^<resolved-major.minor.patch>"`
(caret range on the currently-resolved version — this allows compatible
patch/minor updates going forward while preventing an unexpected major
jump). Do this for all ~27 entries in one pass.

**Verify**: `grep -c '"latest"' package.json` → `0`.

### Step 3: Reinstall and confirm the lockfile is stable

```bash
pnpm install
git diff --stat pnpm-lock.yaml
```

Expected: `pnpm install` exits 0. The lockfile diff should be minimal or
empty (since you pinned to already-resolved versions) — if `pnpm install`
resolves to *different* versions than what was previously locked (possible
if the caret range and the previous "latest" resolution disagree subtly),
review the diff for anything unexpected (a major version bump) before
proceeding; a pure patch/minor bump is fine and expected in some cases.

### Step 4: Build verification

```bash
pnpm build
```

Expected: exit 0. This is the most reliable signal that pinning didn't
freeze in a broken combination — a full Next.js production build exercises
most of the dependency surface.

**Verify**: `npx tsc --noEmit` → exit 0; `pnpm lint` → exit 0; `pnpm build` → exit 0.

## STOP conditions

- `pnpm build` fails after pinning — do not chase the failure by loosening
  a version back to `"latest"`; instead identify which specific package's
  pin is implicated (bisect by reverting pins one at a time if needed) and
  report which one, rather than reintroducing the `"latest"` pattern.
- `package.json` shows `next` or `xlsx` still (or again) pinned to

  contradicts this plan's "Current state" assumption; STOP and report the
  discrepancy rather than silently including them in this pass (a
  regression there is worth flagging distinctly, not folding into a
  routine pin-cleanup commit).
